# 评测输入、计时范围与结果解读

构建、运行和保存结果的命令见 [运行指南第 5 节](RUNNING.md#5-构建并运行-release-评测)。本项目评测程序和 GoogleTest 正确性测试分开，评测不注册到 CTest。

## 1. 两个程序分别测什么

| 程序 | 主要问题 | 输出规模 |
| --- | --- | --- |
| `dynamic_route_benchmark` | 同一静态地图上，四种算法首次规划的开销是多少？ | 四行算法结果。 |
| `dynamic_route_dynamic_benchmark` | 连续变化后，重新搜索与保留状态的修复分别需要多少工作？ | 六个场景，每个四行结果。 |

两者使用 Release、`std::chrono::steady_clock`、一次不计时预热和 20 次测量。单位 `us` 为微秒，`1000 us = 1 ms`。算法按固定顺序依次运行，未做交错采样、冷缓存控制或统计显著性分析。耗时会随机器、优化、负载、缓存和执行顺序变化。

想直接看地图和最终路线，请使用 [静态路径图示例](RUNNING.md#31-静态地图与路径图推荐)。它是独立的 15×23 演示地图，输出 HTML 图页，不修改本文件中的评测场景或计时范围。

共享参数和校验位于 `benchmarks/benchmark_support.hpp`；动态更新次数在 `dynamic_benchmark.cpp` 中固定为 10。修改场景或重复次数后须重新构建，程序没有命令行参数来修改它们。

## 2. 地图、权值和参照答案

加权地图为 48×64，种子 `20261024`，使用 `mt19937` 及原始整数取模生成。权值从 `0.25、0.5、1、2、5` 中选择，约五分之一格子为障碍。第一列和最后一行保持通行，保证本基线存在路线。起点 `(0,0)`，目标 `(47,63)`，最优代价 `82.75`。

空地图也是 48×64，所有格子通行且权值为 1。默认端点为 `(24,0)` 和 `(24,63)`。所有评测采用 Four 邻接，A* 与双向 A* 使用默认 Automatic 启发式。

参照答案在计时外用 Dijkstra 计算。每个预热和正式结果都在计时外校验是否可达、端点、逐步移动是否合法、路径重算费用，以及是否匹配最优代价。费用比较采用 `1e-9 * max(1,abs(reference_cost))` 的误差范围。不可达结果必须为空路径且代价为正无穷；校验失败返回非零退出码。

## 3. 静态初次规划

每次调用都从新的搜索状态开始。D* Lite 在计时范围内构造、首次规划并析构，标签为 `DStarLiteInitial`，避免把缓存查询与其他算法的新搜索混为一谈。

```text
algorithm,total_cost,expanded_nodes,frontier_pushes,mean_us
```

| 列 | 含义 |
| --- | --- |
| `algorithm` | 算法标签。 |
| `total_cost` | 最后一次已验证结果的代价。 |
| `expanded_nodes` | 最后一次搜索的节点处理次数。 |
| `frontier_pushes` | 最后一次搜索的实际入队次数。 |
| `mean_us` | 20 次独立初次规划的平均微秒数。 |

固定输入的代价与工作量基线如下，耗时以自己机器的实际输出为准：

| 算法 | 代价 | 扩展次数 | 入队次数 |
| --- | --- | --- | --- |
| Dijkstra | 82.75 | 2424 | 2446 |
| AStar | 82.75 | 2297 | 2408 |
| BidirectionalAStar | 82.75 | 4482 | 5215 |
| DStarLiteInitial | 82.75 | 2251 | 3612 |

计时包含搜索初始化、启发式扫描、路径生成及算法内部状态清理。排除地图生成、参照搜索、结果验证、结果路径析构和控制台输出。各次调用返回结果后的处理不计入搜索耗时。

## 4. 六个动态场景

每个场景、每种算法、每轮试验都复制独立地图。静态算法在每次变化后重新搜索；D* Lite 每轮仅构造一次，完成初次规划后保留状态。一次完整试验为初次规划加 10 次更新；预热也是完整试验。

| 场景 | 变化 | 起点/目标 | 初始 → 首次更新 → 最终代价 |
| --- | --- | --- | --- |
| `weighted_on_path` | 加权地图原路径中间格 `(18,36)` 阻塞/恢复，五轮。 | `(0,0)` → `(47,63)` | `82.75 → 89.25 → 82.75` |
| `open_on_path` | 空地图原路径中间格 `(24,32)` 阻塞/恢复，五轮。 | `(24,0)` → `(24,63)` | `63 → 65 → 63` |
| `open_off_path` | 空地图路径外 `(0,32)` 阻塞/恢复，五轮。 | 同上 | `63 → 63 → 63` |
| `open_terrain_on_path` | `(24,32)` 权值 `1→5→1`，五轮。 | 同上 | `63 → 65 → 63` |
| `open_terrain_lower_bound` | `(24,32)` 权值 `1→0.25→1`，五轮。 | 同上 | `63 → 62.25 → 63` |
| `open_moving_start` | 地图不变，沿原始 Dijkstra 路径前进十步，终点固定。 | 起点 `(24,0)` 移到 `(24,10)`；目标 `(24,63)` | `63 → 62 → 53` |

路径中间格由计时外的原始 Dijkstra 路径选择；显式的路径外格会检查确实不在原路径上。所有算法收到同样的更新序列。起点移动的 `starts` 序列也在计时外构造，不根据各算法自己返回的路径改变。

`open_on_path` 与 `open_off_path` 只改变更新位置，适合对照位置影响。加权场景与空地图场景的地图、权值及端点都不同，不能把它们的差异归因于单一因素。

## 5. 动态输出字段与平均值

每个场景先输出 `#` 开头的元数据，再输出表头和四行数据：

```text
scenario,algorithm,initial_us,first_update_us,mean_later_update_us,mean_update_us,total_us,mean_expanded_nodes,mean_frontier_pushes
```

| 列 | 含义 |
| --- | --- |
| `scenario` | 场景标识。 |
| `algorithm` | 算法标识，动态 D* Lite 使用 `DStarLiteRepair`。 |
| `initial_us` | 20 轮初次规划的平均耗时，D* Lite 包含构造。 |
| `first_update_us` | 各轮第 1 次更新的平均耗时。 |
| `mean_later_update_us` | 各轮第 2～10 次更新的单次平均耗时，共 180 次。 |
| `mean_update_us` | 全部更新的单次平均耗时，共 200 次。 |
| `total_us` | 每轮“初次规划 + 十次更新”的平均总耗时。 |
| `mean_expanded_nodes` | 单次更新平均节点处理次数，不包含初次规划。 |
| `mean_frontier_pushes` | 单次更新平均入队次数，不包含初次规划。 |

例如，忽略输出四舍五入后，应满足：

```text
mean_update_us = (first_update_us + 9 * mean_later_update_us) / 10
total_us = initial_us + 10 * mean_update_us
```

元数据中的 `initial_cost` 是初始最优代价，`changed_cost` 是**第一次更新**后的代价，`final_cost` 是第十次更新后的代价。移动起点场景中，后续代价继续逐步降低，并不是始终等于 `changed_cost`。表格行中的节点/入队次数是多次更新的平均值，因此可以有小数。

## 6. 动态计时包含什么

单次更新计时包含地图 setter 或 `move_start`，随后包含完整搜索/修复及路径生成。D* Lite 初次计时包括构造与第一次 `plan()`；后续通过同一个对象规划。静态算法内部临时搜索状态在调用内释放，也计入耗时。

以下工作不在动态 `total_us` 中：地图复制、起点序列生成、参照搜索、路径校验、输出、返回结果的路径析构，以及该轮持久 D* Lite 对象最后的析构。`total_us` 是计时间段之和，不是整个进程的墙上时间。

因此同时查看 `mean_update_us` 和 `total_us`：更新快不一定抵消初始化成本。扩展计数也不是所有工作量的代理，扫描、队列管理和路径生成同样耗时。

## 7. 如何理解不同场景

### 路径外障碍与起点沿已知路径移动

`open_off_path` 和 `open_moving_start` 中，已有到目标的距离可能足够，D* Lite 更新时可以不新增扩展和入队。它仍须处理接口调用并输出路径，耗时不会为零。起点移动场景展示的是固定地图上沿已知路线复用状态，不保证覆盖所有惰性重排分支。

### 权值升高

将路径格权值从 1 提高为 5，不改变全图最小权值 1，可以走普通一致性修复。该格仍可通行，只是进入更贵；在这个地图上绕两步更便宜，所以最优代价与阻塞场景恰好同为 65，两者的边集合/边费用并不相同。

### 权值低于缓存下界

首次从 1 降到 0.25 会让 D* Lite 检查最终最小权值、降低启发式尺度、清空旧队列并重新放入所有不一致节点。g/rhs 和待修复变化保留。当前场景没有起点移动，km 原本就是 0。

恢复权值为 1 后，缓存下界保持为 0.25；下一次降到 0.25 不再降低下界。因此每轮试验只触发一次这种重建。`first_update_us` 展示首次完整更新，`mean_later_update_us` 混合五次恢复和四次再次降低。两者的差值不是纯粹的队列重建耗时。

静态 A* 每次搜索按当前地图重新取下界，恢复时可用 1；D* Lite 保留仍然有效但较弱的 0.25。这也会改变搜索工作量。全图扫描不计入扩展数，但计入时间；实际重入队计入 pushes。

### 为什么更复杂的算法可能更慢

双向搜索维护两套队列/距离/父节点；弱启发式与保守停止规则可能带来大量重叠工作。D* Lite 维护 rhs、版本号和待修复队列，变化也可能传播很远。当前加权基线中，初始 Manhattan 下界仅为 `110*0.25=27.5`，实际最优代价为 `82.75`，下界较松。

这些机制解释了潜在开销，但单次计时不能精确分离各部分成本。保留慢于基础算法的场景，才能看到适用条件；本项目不根据这六个固定输入给出普遍排名。

## 8. 按源码核对测量流程

先看 `benchmark_support.hpp` 的地图和 `validate`；静态程序看 `measure` 与 `main`；动态程序依次看 `run_trial`、`measure`、`run_scenario` 和 `main`。

`run_trial` 负责单轮计时及事件后校验；`measure` 负责预热与平均值；`run_scenario` 生成参照费用、共享更新和起点序列；`main` 固定六种输入。评测结果应保留元数据、编译模式和完整输出，重新对比时在同一构建环境运行。
